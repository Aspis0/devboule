# Apprentice + Day-0 Merge Design

## 1) Data flow (canonical v1)

1. **`training_export` rail**
   - Rust remains the only producer: per-project `.aspis-training/{findings.jsonl,pairs.jsonl,blobs/}`.
   - No Python hook runs in Censor's hot path.

2. **`oracle.evals.assemble_pairs`**
   - Existing trainer path runs `from oracle.evals.assemble_pairs import assemble`.
   - It emits normalized `{prompt, rejected, chosen, meta}` records from dirty -> clean transitions.

3. **`ingest` → `cluster.assign`**
   - `ingest()` resolves each source, deduplicates by stable hash, builds embeddings, and appends pairs to `data/pairs.jsonl`.
   - `cluster.assign()` routes each pair to an active cluster, maintains centroids, counts, and streak state.

4. **Night ORPO trigger**
   - `cluster.ready()` returns clusters where `count >= CLUSTER_TRIGGER` (currently `30`).
   - If no ready clusters, nightly loop exits early with no training.

5. **Nightly ORPO train / Pass@1 gate**
   - The nightly driver builds a train set from cluster pairs plus the bounded replay buffer.
   - ORPO runs on a timestamped adapter path generated by `next_adapter_path()`.
   - `pass_at_1` benchmark on gold/replay tasks must pass threshold and must not regress on gold by `REG_TOLERANCE`.
   - Only if gate passes:
     - promote adapter by changing the `adapters/active.txt` pointer
     - update cluster streak / history.

6. **Versioned adapter lifecycle**
   - `next_adapter_path()` assigns timestamped directories such as `adapters/20260611T153000Z`.
   - `active.txt` is only changed by successful benchmark path; `previous-active.txt` keeps rollback possible.
   - No overwrite of historical candidates.

7. **Runtime serve**
   - Existing serving stack uses the configured local model + adapter override:
     - oMLX and Ollama paths already support explicit local model/adapter targeting.
- Day-0 bootstrap output remains explicit: `MODEL_PATH` points at `oracle/training/day0/qwen3-27b-day0-mlx`; the bootstrap script copies the warm-up ORPO adapter into a versioned apprentice adapter dir and writes `oracle/training/apprentice/adapters/active.txt`.

## 2) Day-0 decisions and risk verdicts

### Day-0 prune stack
- **Vocabulary prune** is now an *optional experiment*; it is off by default and refuses to run without:
  - `--enable --accept-risk --apply --rewrite-tokenizer`.
- **Layer prune** remains deterministic and sequential, with MPS/CPU path hardening and no hidden edits.
- **Quantized MLX conversion** is enforced in the run path with explicit 4-bit arguments.
- The default path runs layer pruning from the dense HF model id, not a vocab-pruned local directory.

### Risk verdicts
- **HIGH risk / LOW-to-moderate gain**: vocab pruning can silently alter token boundaries and break alignment; this is now explicitly gated and requires tokenizer rewrite confirmation.
- **MEDIUM risk / moderate gain**: layer pruning changes architecture behavior and should stay Night-0 experimental and measured by Pass@1.
- **LOW operational risk**: data ingest/cluster/night ORPO remains in existing flow with the same trigger + rollback gate.

## 3) Training data preparation notes (file-aware split)

`day0_prepare_data.py` now:
- writes all artifacts under `oracle/training/day0/data/...` with fixed output paths.
- does not rely on random row-only split for validation.
- computes train/valid by source **file bucket** to reduce leakage:
  - all records for one file stay in the same split;
  - validation target kept at the required capacity first by whole-file bucket packing.

This rule applies to both:
- SFT rows (`instruction` + `output` -> chat messages),
- ORPO rows (`prompt` + `chosen` + `rejected`).

## 4) Privacy and data hygiene

- Keep only model-safety fields in exports: no runtime secrets, tokens, or raw environment variables.
- Avoid storing local project source code if not needed; only the pair text and optional file labels should be retained.
- Maintain replay caps and bounded writes in cluster persistence (`replay.jsonl` and bounded pairing state).
- Treat both exported corpus and generated pair files as local developer data; clean stale paths before sharing the repo.

## 5) v1 scheduler posture

- **Current v1**: manual/cron orchestration via existing `night_run.py` entrypoint.
- **v1 hardening goal**: keep `night_run.py` as the authoritative control plane.
- **Future automation**: introduce macOS `launchd` launch agent:
  - run nightly around a fixed window,
  - emit rotated logs,
  - enforce single-instance lock + failure backoff,
  - keep manual trigger (`python night_run.py`) intact.

## 6) ORPO command/package grounding

- For forked flow, warm-up ORPO should use:
  - `python -m mlx_lm_lora.train --model ... --train --train-mode orpo ...`
- Keep `python -m mlx_lm.lora` for SFT unless package changes in your MLX fork.
- Do not call ORPO through `mlx_lm.lora` in this branch, because this repo baseline keeps ORPO tied to the forked package path above.
- Grounding checked 2026-06-11:
  - Official `mlx-lm` LoRA docs describe `mlx_lm.lora` for LoRA/QLoRA and note QLoRA when `--model` points at a quantized model: https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md
  - The `mlx-lm-lora` package documents the main command as `mlx_lm_lora.train` and ORPO usage with `--train-mode orpo`: https://pypi.org/project/mlx-lm-lora/
- Pass@1 sandbox posture in `oracle/training/apprentice/night_run.py`: generated code runs from a temp cwd with `python -I -u`, `HOME` and `USERPROFILE` set to that temp cwd, `PYTHONPATH` excluded, proxy env removed, and resource/timeout caps where the host supports them.
- Residual risk note (not blocked in v1): network is **NOT** blocked because there is no reliable cross-platform, unprivileged network-deny mechanism. Treat gold tasks as locally curated inputs only; do not benchmark arbitrary untrusted prompts until a host-level sandbox is added.
- Verify-on-Mac checklist:
  - VERIFY-ON-MAC: install the pinned ORPO fork with `python -m pip install "mlx-lm-lora==2.1.0"`.
  - VERIFY-ON-MAC: run the documented ORPO command shape exactly: `python -m mlx_lm_lora.train --model ... --train --train-mode orpo --data ... --iters ... --batch-size ... --lora-rank ... --adapter-path ...`.
  - VERIFY-ON-MAC: confirm generated code execution uses temp HOME/USERPROFILE and Python `-I` isolation in all runner paths (`oracle/training/apprentice/night_run.py`).

## 7) Qwen3.6-27B dense vs Qwen3.6-35B-A3B MoE

- Dense 27B has simpler architecture expectations and lower risk of routing-path regressions.
- 35B-A3B MoE should improve quality at large token budgets, but inference profile, quantization behavior, and adapter compatibility are **unknown** on this exact stack.
- Unknowns to verify on Mac before adopting:
  1. exact `mlx_lm` conversion flags supported by your installed package,
  2. whether ORPO warm-up accepts same `train-mode orpo` path under MoE,
  3. Peak memory and throughput at target context lengths.
