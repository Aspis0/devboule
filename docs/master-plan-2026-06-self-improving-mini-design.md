## 0. North star

Two complementary training levers over ONE shared data rail (`.aspis-training/pairs.jsonl` + Censor verdicts as objective scorers):
- **ORPO** = trains WEIGHTS, local models only (Qwen via oMLX). Runs **nightly on the Mac** (mlx-lm-lora, QLoRA/QAT) — data never leaves the machine.
- **SkillOpt** = trains TEXT (`SKILL.md`) for FROZEN models (claude/codex/design) we can't fine-tune. Runs nightly via **SkillOpt-Sleep**.

The runtime loop: coder orders → **mini WRITES** (local Qwen, emit-edits → Rust applies, sandboxed, read-only Oracle) → **deterministic Censor** verdict → **mini fixes ONCE → stops** → **coder reviews** (Censor + Gemma tier + its own Sonnet review pass) → fixes → Kanban `review` → human-gated final reviewer. Every mini output is a reviewed draft. Four independent security layers (server allowlist, Seatbelt FS, Rust diff/revert guard, bounded loop).

Hardware: **Mac = inference (day) + nightly training (night) + data collection**. **Scaleway = only the heavy one-shot initial ORPO warmup.** No macOS 27 dependency anywhere.

- **🔥 LOCAL-MODEL LATENCY — the "10-minute single-file review" fix (added 2026-06-14, from the Kairos study + the local-speed investigation; pairs with [[censor-local-investigation-2026-06-13]] which already concluded "no fast+local+semantic censor exists — deterministic gate + Sonnet/Oracle on the DIFF + a future fine-tuned small model").** Why the local Censor/mini takes ~10 min (or fails) on a 1k-line file, and the concrete fixes — measured, not guessed:

(c) the **dense 27B is just slow (~14.5 tok/s measured)**; any long output = minutes — the A3B MoE is **4× faster (~60 tok/s)** for the same output.

A generic model must GENERATE a long CoT to catch semantic bugs — that generation *is* the unbounded latency; removing it removes the bug-catching too. No knob on a generic model escapes the depth=think-tokens=time tradeoff.

For NEW files there's no diff → the input is large and the deep-review tradeoff above applies in full. Fix = wrap the LLM in deterministic tools, split across **TWO latency tiers** (mixing them is the trap):
    - **TIER A — interactive verdict, SECONDS, BLOCKS the write→fix-once→stop loop**, on the single new/changed unit: **(1) tree-sitter** (ms, one grammar/language) — extract review units with EXACT AST boundaries (replaces the Rust-only brace heuristic in `review-experts/src/extract.py`; gives the JS/TS extraction we lack), inject VERIFIED syntactic facts as context (signature, free symbols, type annotations, control-flow shape), and **GROUND the output** (drop any finding whose `line`/symbol/call the AST contradicts — the load-bearing anti-hallucination step); **(2) semgrep** (curated/focused ruleset, ~seconds) — known anti-patterns (`==` vs `===`, `unwrap()` on `Result`, `await`-in-loop); **(3) per-language type/lint** — oxlint (ms), tsc, clippy, pyright; **(4) the fine-tuned LLM** judges the RESIDUAL; **(5) post-LLM merge** = AST-grounding + **cross-check vs the deterministic findings** (corroboration → confidence: a deterministic hit near an LLM finding RAISES confidence, an authoritative contradiction LOWERS it; dedup). semgrep here CORROBORATES, it does NOT filter the LLM. **Honest cost inside Tier A:** tree-sitter / oxlint / focused-semgrep are instant; **tsc and clippy are NOT** (clippy COMPILES → tens of seconds cold; tsc is project-graph-dependent) → budget them or run async-within-A, never assume free.
    - **TIER B — deep complete-check, MINUTES, ASYNC, NON-blocking, per-commit/nightly over the MODULE/repo (NOT per-file):** **Joern / CPG** — interprocedural data/control-flow + taint, works on fragments, no full build. Findings land LATER on the PR/Kanban and feed the P7→P13 training pairs. This is the owner's instinct (slow tools run alongside and arrive at the end) done RIGHT: a SEPARATE tier with a coarser cadence, never in the Tier-A loop. Why CPG tools can't be per-file: their power is interprocedural/whole-program; on an isolated new file with unresolved imports they lose most of their value → they WANT module/repo context.
    - **DROPPED, deliberately (owner-confirmed 2026-06-14):** **ANTLR** — a parser GENERATOR giving the same parse tree as tree-sitter, heavier, all tooling by hand: pure redundancy (tree-sitter already covers our languages). **CodeQL** — its license FORBIDS private/commercial codebases without GitHub Advanced Security → unusable in the Devboule PRODUCT (users run on their own private repos); Joern gives ~70% of the interprocedural depth with a clean license. OUT of the product architecture (ties to the PRODUCT GENERALITY rule — license is a real product constraint, not branding).
    - **The complete check is a UNION, not a mega-pass:** (Tier-A instant verdict that unblocks the fix) + (Tier-B findings that arrive later on the PR). A synchronous all-tools pass would just resurrect the 10-minute problem.
    - **Discipline + ceiling:** add ONE tool at a time, ADVISORY-first, measure its FP-rate on the repo, promote to gate only when clean — FP-heavy tools poison both the verdict AND the ORPO labels (the P2 lesson). **Sequencing:** Tier A (tree-sitter + semgrep + tsc/clippy + fine-tuned LLM + grounding) IS the product → build first; Tier B (Joern) is a separate security-depth project → after. **Measure FPR reduction per added tool in P15.** **Honest ceiling:** tree-sitter is syntax-only (no type-inference / data-flow) — grounding kills the STRUCTURAL hallucination class (fake line/symbol/location), the SEMANTIC class (real line, wrong judgment) is what Joern / clippy / the cross-check catch. Not novel in the abstract (grammar-constrained decoding, symbol grounding, verifier models exist); the leverage is the application — a deterministic sandwich around a small LOCAL reviewer whose granularity + AST coordinates we own. Folds into the local-review design doc + the P2 gate + P13 + P15.
  - **⚡ SPECULATIVE DECODING — a real decode-speed lever for the DENSE local reviewer, UNLIKE the hybrid models (added 2026-06-14, owner ask; the Kairos speed study `kairos/SESSION_2026-06-14_speed-investigation.md` + `TRACK2_MTP.md` proved SD DEAD on the local Qwen3.6 models — but that verdict is ARCHITECTURE-SPECIFIC, not general, and does NOT apply to our reviewer).** Kairos killed SD on the **hybrid GatedDeltaNet + MoE** Qwen3.6 (27B: MTP **0.87×**; 35B-A3B custom kernels **≤1.04×**) because a multi-token VERIFY there costs **~1.86×** a single token (the linear-attn recurrence scales with #tokens; the MoE router reads the UNION of the tokens' experts) → acceptance was 85-96% but the architecture eats the win (*"the architecture, not the head or the software, defeats the speedup"*). **Our reviewer is a pure DENSE 8B (Qwen3-8B / Seed-Coder-8B)** — the OPPOSITE regime: a 2-token verify ≈ a 1-token verify (weights read once, decode is memory-bound → the extra token is ~free).
