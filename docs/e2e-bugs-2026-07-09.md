**Repro fedele all'app** (spawnato `sidecar.mjs` con l'esatto env dell'app + prompt `{"type":"prompt","message":"ciao"}`):
- Il sidecar riceve il prompt, apre il turn col provider/model GIUSTI (`provider:"openai", model:"Qwen3.6-35B-A3B-4bit-DWQ"`)…
- …ma l'assistant `message_start` esce con **`content:[]`, `output:0` token, `stopReason:"stop"`** → **RISPOSTA VUOTA**. Nessun delta, nessun `message_end` in ~85s. → console **idle/vuota**.
- Poiché Rust non risponde mai a `classify_prompt`, ogni prompt colpisce il **timeout 5s** di `requestClassification` (`sidecar.mjs:156`) → default classification → `applyPigeonRouting` chiama `session.setModel(resolved)` con provider/model `null` → **null-deref** `Cannot read properties of undefined (reading 'provider')` (catchato, "keeping session model", `sidecar.mjs:187-203`).

**VERDETTO:** il bug NON è PATH/config/modello/refactor. È **il turn del pi sidecar che produce output vuoto per l'orchestrator locale oMLX** (`sidecar.mjs:handlePromptCommand` → `session.prompt`), riprodotto deterministicamente mentre la chiamata diretta a oMLX funziona. Concause nel sidecar: (1) **classificazione Pigeon rotta/non implementata lato Rust** → 5s di ritardo + null-deref ad ogni prompt; (2) il turn `session.prompt` via pi SDK non genera token (0 input/0 output) — probabile handle di sessione/modello corrotto o config models.json incompatibile.

### 🎯🎯 CAUSA RADICE DEFINITIVA (proxy-capture + replay, 2026-07-09) — CONFERMATA AL 100%

Ho messo un **proxy-logger tra sidecar e oMLX** e catturato la richiesta REALE del pi SDK:
`POST /v1/chat/completions`, `model:Qwen3.6-35B-A3B-4bit-DWQ`, `messages:[system enorme, user "ciao"]`, `stream:true`, `store`, `stream_options`, `tools`, `max_completion_tokens`. **La richiesta è corretta e include il messaggio utente** — quindi NON è payload malformato.

Riproducendo la richiesta con curl, lo stream torna così: **87 delta `reasoning_content`** + **1 solo delta `content`** (`"\n\nCiao"`, in fondo), `finish_reason:stop`.

**IL BUG:** `Qwen3.6-35B-A3B` è un **REASONING MODEL**. In streaming emette quasi tutto come **`reasoning_content`** (campo stile DeepSeek-R1) e la risposta reale come un minuscolo `content` finale dopo decine di secondi di pensiero. **Il pi sidecar (`api:"openai-completions"`, `supportsReasoningEffort:false` in `buildCustomModelsJson` `sidecar.mjs:269`) legge SOLO `delta.content` e SCARTA `reasoning_content`** → per tutta la (lunga) fase di reasoning la console non mostra nulla → **idle**; e se `max_completion_tokens` si esaurisce nel reasoning, il `content` finale è vuoto → **zero risposta**.

Prova incrociata: chiamata diretta `stream:false` → il server fonde reasoning dentro `content` → **funziona**; sidecar `stream:true` → reasoning separato e ignorato → **non funziona**. Coerente con tutto.

**Pigeon NON è la causa** (owner aveva ragione). È un red herring, anch'esso rotto (mai implementato lato Rust → 5s timeout + null-deref `setModel` ad ogni prompt), ma indipendente dal "non risponde".

### DIREZIONE FIX (prioritizzata, CONFERMATA)
1. **[core] Il sidecar deve gestire `reasoning_content`.** Nel subscription della sessione pi, mappare i delta `reasoning_content` (oltre a `content`) e inoltrarli come output "thinking" alla console — così l'utente vede che il modello sta lavorando invece di "idle", e il `content` finale viene catturato. Verificare come il pi SDK espone i reasoning delta (`docs/models.md`/`custom-provider.md`); potrebbe servire marcare il modello come reasoning nel models.json (compat) invece di `supportsReasoningEffort:false`.
   - Alternativa/aggiuntiva: per l'orchestrator locale usare un **modello NON-reasoning** (es. `Qwopus3.6-35B-A3B-Coder-4bit` è servito da oMLX) o disabilitare il thinking del modello, finché il rendering del reasoning non è pronto.
2. **[Pigeon] Gate esplicito:** se Rust non implementa `classified`, il sidecar NON deve chiamare `requestClassification` (oggi lo fa sempre → 5s + null-deref ad ogni turn). Skippare la classificazione o non-fatale il null-deref.
3. **[robustezza] Feedback:** mostrare stato "thinking…"/progress durante il reasoning e un banner se il turn finisce senza `content`, invece della console idle silenziosa.
4. **[minore] Resolver `node`/`pi` esplicito** per il build packaged (Finder/Dock) — non è la causa attuale (owner lancia da terminale) ma romperebbe la versione packaged.

**Come fixare (owner rules):** modifiche a `sidecar.mjs` = **pi coder (mimo)** + loop see-fix-see col repro-via-proxy come oracolo, NON coding inline Claude. Il repro deterministico è: spawn `sidecar.mjs` con env `DEVBOULE_PI_PROVIDER=openai DEVBOULE_PI_MODEL=Qwen3.6-35B-A3B-4bit-DWQ DEVBOULE_PI_BASE_URL=http://127.0.0.1:8000/v1 OPENAI_API_KEY=mlx DEVBOULE_AGENT_ROLE=orchestrator DEVBOULE_PI_SANDBOX=false` + prompt `{"type":"prompt","message":"ciao"}` su stdin → oggi assistant `content:[]`.
